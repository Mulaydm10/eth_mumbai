## Bridge 1: ENF Witness (mains-hum clock from forensic audio analysis)
- Source mechanism: grid frequency wanders randomly around 50 Hz; that wander is audible/inducible in recordings made near mains. Extract the ENF trace from a clip, correlate against a reference trace logged by a mains-connected monitor, best match = when it was recorded; discontinuities reveal splices. Longer clips match better. https://www.mast.umd.edu/files/paper_ENF/conf_paper3_WIFS12.pdf , https://drum.lib.umd.edu/handle/1903/14790
- Problem (one sentence): Anyone can back-date or reuse a damage photo/video, so insurers and courts cannot trust "this was filmed at the time of the accident"; honest claimants and insurers both pay for the fraud.
- Who suffers: motor/crop/property policyholders (slow, suspicious claims) and insurers.
- Evidence URL: CBI Gwalior case, 411 claims with reused damage photos https://www.outlookmoney.com/personal-finance/cbi-books-three-in-gwalior-over-rs-430-crore-motor-insurance-fraud ; human detection of AI-manipulated damage photos ~50% https://www.milliman.com/en/insight/accidents-that-never-happened-genai-motor-fraud
- Transfer: Dhruv's RF/signal-processing background fits; extract ~50 Hz hum from phone mic (or video flicker / light sensor) and publish a signed time-attestation. India runs one synchronous grid (my inference, mild confidence) so a single reference stream covers the nation. What breaks: phone mic high-pass filters/AGC may kill 50 Hz (use 100 Hz harmonic, or the flicker of mains lights via camera rolling shutter); battery-only/outdoor recordings carry no hum; we must run our own reference recorders (self-sourced truth; Grid-India PMU public data exists only as historical research sets https://data.mendeley.com/datasets/bvwh9d6227/4, live feed NOT found); ENF spoofing by replaying a hum is a known attack.
- Sponsor stack: Arkiv (reference ENF samples as attribute-indexed entities with TTL, queried by time window; the query-by-attribute and expiry are the actual storage need) + World ID (claimant is a unique human; request -> attest -> validated -> denied/expired path for a backdated clip). 2 sponsors, 0 EF.
- Phone role: central: records the clip, extracts hum features, optionally also logs IMU/light sensor.
- Candidate Level-3: ENF extraction + match with a measured false-accept/timestamp-error figure on real recordings in Mumbai buildings.
- WOW: judge records 15 s of the room on a phone; app prints the wall-clock window it was recorded in to within seconds; then a clip edited/back-dated is rejected live with the splice point shown.
- Self-measurable number: median timestamp error (s) and false-accept rate over 100+ recordings across 5+ locations; minimum clip length for 95% correct match.

## Bridge 2: Incident-pinned black box (flight recorder overwrite loop)
- Source mechanism: CVR/FDR write to crash-protected memory in a continuous overwrite loop (about 2 h of audio), so only the window before the event survives. The 2-hour limit was criticised after MH370/AF447. https://planefyi.com/systems/cockpit-voice-recorder/ (secondary)
- Problem: After a hit-and-run or road accident there is rarely any evidence, so the victim cannot even file against an insurer.
- Who suffers: road-accident victims/families in India; hit-and-run is ~15% of accidents, ~18% of deaths (2022, figures differ). https://www.gicouncil.in/news-media/gic-in-the-news/hit-and-run-motor-accidents/ , https://theprint.in/india/6-yrs-after-adding-provision-in-mv-act-centre-drafts-interim-compensation-scheme-for-hit-run-victims/2736976
- Transfer: the phone is the recorder; the overwrite loop is Arkiv TTL (data expires by default, so privacy by expiry); an IMU-detected crash/fall extends TTL of the preceding N minutes (the "pin"). Breaks: phone must be mounted/on; encryption/key escrow so the pinned data is not public; false triggers on potholes; crash-survivability is moot (data goes off-phone continuously).
- Sponsor stack: Arkiv (TTL ring buffer plus pin = extend expiry; a rolling-retention need that is its core feature) + 0G Physical AI (pocket device: on-device/0G inference decides "incident vs pothole"; safe-stop behaviour = if 0G unreachable, keep local ring and fail towards retaining). 2 sponsors.
- Phone role: central (IMU, mic, camera, GPS).
- Level-3: crash-vs-pothole classifier plus retention proof (the pre-event window is provably present at claim time, absent otherwise).
- WOW: drop/shake a phone-in-a-model-car; seconds later the pre-impact 5 min is "pinned" and a claim viewer queries it, while an un-pinned older window visibly expires.
- Number: precision/recall of incident trigger on N staged drives/drops; false pins per hour; pre-event window actually retained (s).

## Bridge 3: Consent artefact with expiry for wallet history (India Account Aggregator)
- Source mechanism: a consent manager issues a digitally signed consent artefact when a data user requests data; data flows between provider and user encrypted, the manager never reads it; >100M consents by Aug 2024. https://www.medianama.com/2024/08/223-100m-consents-on-indias-account-aggregator-framework/ , https://www.fiskil.com/open-finance-tracker/standard/account-aggregator-india (third-party summary; artefact field details NOT confirmed)
- Problem: To get a loan or a job, crypto earners must hand over their whole wallet history (or screenshot it) with no purpose limit, no expiry, no revocation.
- Who suffers: crypto-paid freelancers/gig workers wanting credit. EVIDENCE GAP: I have no URL showing demand for wallet-history underwriting; AA counts above show only the Indian consent model works at scale.
- Transfer: consent artefact = an ENS subname issued to the requester with an EAC role scoped by purpose; the data lives as encrypted Arkiv entities whose TTL equals consent duration; reads go through Anon-RPC so the fetcher is not observable to the chain observer. Breaks: Arkiv data is public unless encrypted, so "revocation" means key rotation; true deletion impossible on a ledger; legal weight of artefact absent.
- Sponsors: ENS (ENSv2 roles/subnames are the consent object) + Arkiv (expiry = consent expiry) + EF Anon-RPC (hide who is reading). 3 sponsors, 1 EF. Each is load-bearing in the design.
- Phone role: weak (approval UI / biometric consent).
- Level-3: consent lifecycle where revoke/expiry measurably denies reads (key rotation + role removal), with an attack test (replay old artefact after revoke).
- WOW: lender is granted 24 h access live; the "data user" screen reads it; user taps revoke; the next read fails in under a few seconds and an expired artefact auto-vanishes.
- Number: revoke-to-denied latency; number of attack attempts blocked of N replay/escalation attempts.

## Bridge 4: CFAR swap guard (radar constant false alarm rate)
- Source mechanism: threshold = alpha x mean of reference cells around the cell under test (guard cells excluded), alpha set from desired false-alarm probability, so false alarms stay constant whether background is noise or clutter; weakness at clutter edges (OS-CFAR/GO-CFAR variants). https://en.wikipedia.org/wiki/Constant_false_alarm_rate , https://wirelesspi.com/adaptive-thresholding-in-radar-detection-using-constant-false-alarm-rate-cfar-techniques/
- Problem: A fixed slippage setting is a fixed radar threshold: too loose in busy/manipulable moments and needlessly failing in calm ones, so users get sandwiched or reverted.
- Who suffers: DEX traders; est. $409k private-channel victim losses in one 4-month study, ~$60M/yr trader losses per one Cointelegraph estimate; 40% of sandwiches hit low-volatility pools. https://arxiv.org/abs/2512.17602 , https://cointelegraph.com/research/exclusive-data-from-eigenphi-reveals-that-sandwich-attacks-on-ethereum-have-waned
- Transfer: cells = recent blocks' price-impact/size for the pool; cell under test = the incoming swap's expected deviation; guard cells = the user's own pending tx; alpha from a chosen false-block rate, giving a per-swap adaptive max slippage and a "sandwich-likely" flag. Breaks: attackers adapt (they can raise the background); on-chain swap cost; multi-pool routing.
- Sponsors: Uniswap (v4 hook enforcing the adaptive bound in beforeSwap/afterSwap) + EF Anon-RPC (the quote/threshold reads must not leak intent to searchers). 2 sponsors, 1 EF. CAUTION: hook-fee/anti-arb hooks are OFF-THE-TABLE; this one is a user-side protection guard, but a judge may read it as "dynamic hook"; keep the headline as the detector.
- Phone role: none.
- Level-3: the detector, replayed on historical mainnet blocks: detection rate at a fixed false-alarm rate vs fixed 0.5/1% slippage baseline.
- WOW: replay a real sandwiched swap side by side: fixed slippage lets it through, CFAR guard rejects it; slider shows false-alarm rate held constant across calm/volatile hours.
- Number: loss avoided (USD) per 1,000 replayed swaps at 1% false-revert rate.

## Bridge 5: General average for tokenized cargo (York-Antwerp)
- Source mechanism: after a deliberate sacrifice to save a voyage, ship and all cargo contribute pro rata to value regardless of fault; an average adjuster computes shares; cargo is held until each owner posts a bond/deposit/insurer guarantee; settlement takes months. https://bowmanslaw.com/insights/general-average/ , https://www.itic-insure.com/our-publications/intermediary/security-collections-under-general-average-2887/ , https://comitemaritime.org/wp-content/uploads/2023/01/CMI-GA-Guidelines-1.pdf
- Problem: When a ship declares general average, small exporters' goods are frozen until they can post security (Maersk Honam: 42.5% salvage + 11.5% GA of cargo value).
- Who suffers: small exporters/importers (MSMEs) with cargo on a casualty ship.
- Transfer: bill-of-lading as an HTS token; GA declaration freezes release; contribution share computed on-chain from declared value; stablecoin bond posted in one tap, funds returned/trued-up when adjusted. Breaks: legal enforceability (YAR works only by contract incorporation), declared values need an oracle, and sacrifices must be judged by an adjuster, not a contract.
- Sponsors: Hedera (HTS tokenization of the cargo claim, no-Solidity SDK) + Whitechain/Optimism (USDT bonds with no gas step for the payer). 2 sponsors.
- Phone role: weak (photo evidence of cargo, signing).
- Level-3: deterministic GA adjustment engine (sacrifice + salvage + pro rata with value-at-risk) with property tests; time-to-release vs "months".
- WOW: a simulated ship casualty; 40 cargo tokens freeze; each owner taps to post a bond; cargo releases one by one as the bond posts and the adjusted shares sum exactly to the loss.
- Number: seconds from declaration to full release vs weeks baseline (baseline is from sources, ours measured); conservation error = 0 over fuzzed cases.

## Bridge 6: Risk-limiting audit for crowd-sourced physical claims
- Source mechanism: sample random paper ballots sequentially, compute the evidence after each batch, stop when the risk of confirming a wrong outcome is below alpha; sample size depends on margin (illustrative 64k ballots, 8% margin: ~80 comparison vs ~700 polling). https://www.stat.berkeley.edu/~stark/Seminars/foro14.pdf , https://prfound.org/resources/election-topics/risk-limiting-audits/
- Problem: Networks that pay people for phone-sensed physical data (noise, pothole, air quality, Wi-Fi coverage) cannot check each claim, so fakes drain rewards.
- Who suffers: honest contributors (diluted rewards) and data buyers. Evidence: DePIN spoofing summaries, mostly vendor blogs: https://ar5iv.labs.arxiv.org/html/2405.16495 (academic, light), https://www.chainscorelabs.com/blog/depin-building-physical-infra-on-chain/geospatial-consensus/why-geospatial-sybil-attacks-are-the-next-big-threat (vendor, weak).
- Transfer: treat each batch of N claims as an "election"; draw random sample indices from verifiable randomness, re-check them (second phone revisit), run a sequential test (e.g. Kaplan-Markov/SPRT style) and release rewards only when the bound says "fraction invalid < tolerance with 95% confidence". Breaks: the re-check is itself a costly physical act; collusion between checker and claimant; election audits assume a paper trail.
- Sponsors: Chainlink CRE (workflow draws the sample, aggregates the checks, releases funds) + Arkiv (claims as entities with attributes, TTL for audit window). 2 sponsors.
- Phone role: central (claimant and checker are phones).
- Level-3: sequential risk-limiting test with a proved bound, tested against simulated fraud rates.
- WOW: a 200-claim batch with 12% secretly forged; the audit pulls 31 random claims, the risk gauge falls, fails the batch live; a clean batch passes with fewer checks.
- Number: expected checks vs fraud rate curve; actual miss rate at alpha=5% over 1,000 simulated batches.

## Bridge 7: Chit fund without a foreman (rotating auction savings)
- Source mechanism: fixed monthly contributions; each month's pot goes to the member who bids the biggest discount; discount is paid out as dividend to the others (foreman keeps ~5%, statutory ~7%); repeat until all have won once. https://www.5paisa.com/blog/chit-fund-in-india-meaning-benefits-risks-and-rules , https://www.tutorialspoint.com/chit-funds-act-an-overview
- Problem: Informal chits depend on a foreman who can abscond and on winners who stop paying after collecting.
- Who suffers: small savers; deposit-scheme frauds labelled "chit funds" (CBI est. Rs 80,000 crore, contested; many are Ponzi, not classical chits - caveat). https://www.millenniumpost.in/chit-fund-scams-rs-80000-crore-and-counting-140062
- Transfer: contract holds the pot; sealed/commit-reveal discount bids; winner's future dividends are the collateral against default (a real chit mechanism); one-human-one-seat via World ID to stop Sybil bidders. Breaks: winner can still walk away if remaining dividends < unpaid contributions (late-round winners owe little but early winners owe much: needs over-collateral or a guarantor pool); regulated activity in India.
- Sponsors: Whitechain (USDT with no gas for payer, "Payments Nobody Notices": monthly contribution via a standing payment) + World ID (a unique person per seat). 2 sponsors.
- Phone role: weak (approvals, notifications).
- Level-3: auction/default accounting with an adversarial simulation (Dhruv's attack-search strength) showing max loss to honest members under best-response defaults.
- WOW: a 10-member chit run through all months in 60 seconds; a member defaults after winning; the pool visibly absorbs it from forfeited dividends and nobody loses principal.
- Number: worst-case honest-member loss (% of pot) across N adversarial strategies.

# DISCARDED BRIDGES (with reasons)
1. Pharmacovigilance disproportionality (ROR) for wallet-drain reports: mechanism is solid (2x2 table, lower CI >1 https://metricgate.com/docs/reporting-odds-ratio-pharmacovigilance/) but it reduces to "scam-detection analytics"; no phone role, and no evidence found that it is distinct from existing scam-flag tools. Could be folded into Bridge 6 as the test statistic.
2. TCAS complementary-sense coordination: two agents settle opposite maneuvers via a data link (https://planefyi.com/systems/tcas-system/). Maps to agent-to-agent conflict resolution, which sits inside the off-table agent-control family and has no physical anchor. Discarded.
3. Seismic early warning via phone accelerometers (MyShake: multi-phone agreement, server confirmation https://livescience.com/53703-earthquake-detecting-app-myshake.html): Google/Berkeley already ship it; a parametric-insurance payout adds little, phone sensitivity is low, quakes are rare in Mumbai for a live demo.
4. Plimsoll line (seasonal/density-dependent load limits; I did not fetch a source): collapses into lending risk-parameter tuning (Gauntlet-style); no phone role; not tested.
5. Hawala netting (trust brokers, periodic settlement; no source fetched): payments netting is crowded and legally fraught; no Level-3 that is new.
6. Railway token/dead-man's switch: valuable as the "safe stop" behaviour 0G asks for, but only a feature, not a headline; folded into Bridge 2 as a design note.
7. IFF / challenge-response (identify friend or foe): ends up as acoustic/radio proximity challenge-response, which is what finalist Enconomy already did.
8. Cold chain / HACCP critical control points: the phone cannot measure product temperature; needs hardware the team lacks.
9. UPI collect request approval flow: collect requests are an approval-layer pattern that falls under the off-table human-approval agent family; no search done.
10. Ballot-level ENF alternative: using Wi-Fi RSSI as a CFAR input for crowd detection: no problem owner identified.
