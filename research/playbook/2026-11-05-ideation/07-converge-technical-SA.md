## Q2 log: EOA as frame-tx sender; 7702 claim (source: raw.githubusercontent.com/ethereum/EIPs/master/EIPS/eip-8141.md, 1565 lines, fetched via curl into scratchpad c2/eip8141.md; line numbers are that file)
- L725-738 "Default code": "Frame transactions can be used by accounts who do not have deployed code, nor an EIP-7702 delegation indicator via the 'default code' mechanism." VERIFY mode: reads allowed scope from flags; requires "a SECP256K1 signature sig at index sig_index such that resolved_signer == resolved_target and sig.msg == Bytes()", then calls APPROVE(allowed_scope). SENDER/DEFAULT mode: "Return successfully as if calling empty code."
- L1324-1328 "Externally Owned Account (EOA) support": "Thanks to the default code, EOAs today can use frame transactions to reap many benefits of account abstraction, including sending sponsored transactions, paying gas in ERC-20 tokens, batch transactions, and more."
- L450-451 dispatch: "if resolved_target code hash is empty ... execute default code. Otherwise, if resolved_target uses an EIP-7702 delegation indicator, execute according to EIP-7702's delegated-code semantics." => default code is selected ONLY for empty code hash. A 7702-delegated sender runs the DELEGATE's code in the VERIFY frame; the tx is valid only if that code itself calls APPROVE (L443-444: a VERIFY frame that reverts/halts invalidates tx; L ~451 "payer must be set"; L1228 "Only the frame's resolved target can call APPROVE"). 
- => ANSWER Q2: YES a plain no-code EOA can be tx.sender (spec + workshop step_3 uses a fresh code-less key). The forum claim is TRUE in the following precise form: a 7702-delegated EOA does NOT get default-code ECDSA validation; its delegate's bytecode must implement validation/APPROVE. A typical sweeper delegate (execute()/fallback with no APPROVE and no signature check against frame sigs) cannot approve => frame tx from that account is invalid. (Inference from spec; not yet run on devnet.) HIGH on spec reading, MED on "typical sweeper delegate" (need to look at actual bytecode).
- L1058-1061: public-mempool validation rule: reads of EXTCODE/CALL to an address using a 7702 delegation are banned except tx.sender default-code. So public mempool also rejects anything that touches a delegated account in validation prefix.
- L1177: "the transaction is only valid if the sender account's code is either empty or a valid delegation indicator" (that is for OTHER tx types).
- PAYMASTER (L935,953,1097-1145,1163): public mempool admits a pay frame only if (a) canonical paymaster (exact runtime-code match, ecrecover-signer, ETH-balance reservation) or (b) non-canonical paymaster used by <MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER = 1 pending tx; plus generic trace rules: SLOAD only on tx.sender storage (L1093), no reads outside tx.sender (L1057). L1330-1334: "any EOA can be a paymaster thanks to default code". => ERC20 paymaster (must SLOAD token balance/allowance of sender in token contract = third-party storage) is NOT admissible to public mempool except 1 pending tx, and fails the storage rule entirely; that is the 'only alt mempool' feature in sponsor text.

## Q3 log: sponsor/paymaster frames and alt-mempool rules
- EIP-8141 Example 3 "Sponsored Transaction (Fee Payment in ERC-20)" (L1383-1399): frames [0 VERIFY APPROVE_EXECUTION target=sender; 1 VERIFY APPROVE_PAYMENT target=Sponsor "checks that the next frame is an ERC-20 send of the right size to the sponsor"; 2 SENDER ERC-20.transfer(Sponsor,fees); 3 SENDER target call; 4 DEFAULT Sponsor post-op]. So YES: a separate payer frame pays gas; ERC20 paymaster paid from SENDER's tokens in the same tx is a spec'd pattern, and "Trustless pay-with-ERC-20 sponsor" (L1455) is costed at +150 bytes. HIGH.
- EIP L1399 (QUOTE, load-bearing for Q4): "to be included in the public mempool under the current model, sponsors must accept some risk of frontrunning by the sponsee who can zero out their ERC-20 balance before the sponsored transaction lands on-chain."  i.e. the spec itself names the race on the sender's token balance.
- Public mempool (L935,953,1130-1142): non-canonical paymaster limited to MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER=1 pending tx; validation may SLOAD only tx.sender storage (L1093) => an ERC20 paymaster reading token balance(sender) or allowance is rejected by public mempool.
- Alt-mempool docs (docs.altmempool.wtf/rules/*; page self-labelled AI-generated, and says sidecar != ERC-8421 draft, many (TBD)):
  * STORAGE-000..033: sender may read storage ASSOCIATED with tx.sender in an external contract if the account already exists (021) [ASSOC-020: slot=keccak256(A||x)+n, n in 0..128, covers ERC20 balances mapping]; an UNSTAKED non-sender entity (e.g. paymaster) gets NO access to other contracts' storage; a STAKED entity gets read-only any storage (032) and write to slots associated with itself (033); pre_verify frames (writable) exist for paymaster state updates. => an ERC20 paymaster reading token.balanceOf(sender) MUST be staked in the alt mempool. 
  * STAKING-010: staked = stake >= MIN_STAKE_VALUE & unstake delay >= MIN_UNSTAKE_DELAY; "There is no penalization mechanism ... stake is never slashed. It exists only as a configurable mechanism for Sybil attack prevention."
  * REPUTATION-220: unstaked sponsoring payer (good rep) may have at most opsAllowed pending txs; REPUTATION-010/020: BANNED = excluded, THROTTLED = capped. Reputation is seen-vs-included; it punishes txs admitted-but-not-included.
  * SOLVENCY-010: payer balance minus reserved pending max cost; default-code (EOA) payers bounded only by solvency.
  * PREFIX-100: default-code accounts exempt from alt-mempool rules; prefix shapes [self_verify], [only_verify, pay], deploy variants.
  * SIGNATURE doc: sender_approved flag covers ALL following SENDER frames; wallet should sign the canonical sig hash which commits to every frame (default code uses empty msg => sighash over all frames) -- good: a rescue bundle signed by victim cannot be edited to redirect.

## Q4 log: adversarial claim (analysis from spec/docs read above; NOT executed on devnet)
Evidence:
- LIFECYCLE-020 (docs.altmempool.wtf/rules/lifecycle): two txs of the same sender with the same nonce_seq and overlapping keys conflict; the later is a replacement "valid under every rule", needs >=10% bump of max_fee_per_gas AND max_priority_fee_per_gas, and "A replacement may name a different factory or payer." => owner-vs-attacker for the same account is a pure fee auction, and the sponsor can change mid-race. Nothing in the rule distinguishes owner from key-holder.
- guides/keyed-nonces: with EIP-8250 keys, "linear and keyed transactions of one sender do not block each other" (sidecar); disjoint key sets coexist => attacker need not even replace the owner; both sit pending, first included wins; the owner's tx is not protected by being first in the mempool. Also per-key limit 4, unstaked sender 64 pending.
- SIGNATURE doc / default code: owner's signature (empty msg) commits to the whole frame list (sighash). Anyone with the key can sign an alternative frame list. No identity beyond the key exists at the protocol layer.
- EIP-8141 L1399 itself flags: sponsee "can zero out their ERC-20 balance before the sponsored transaction lands on-chain" (frontrunning risk for the paymaster) => in the leaked-key case the 'sponsee' is both owner and thief.
- STAKING-010: "no penalization mechanism... stake is never slashed. It exists only as a configurable mechanism for Sybil attack prevention." REPUTATION is seen-vs-included per entity (sender, payer, factory); a thief whose sweeps get included raises the paymaster's reputation, not lowers it. A paymaster that is BANNED (REPUTATION-010) denies BOTH parties.
ANSWER Q4 (precise):
 (a) Yes, symmetric: if a staked ERC20 paymaster sponsors "any sender holding tokens whose SENDER frames pay the paymaster in tokens", then an attacker holding the same leaked EOA key can sweep ERC20 from a zero-ETH EOA via the same paymaster in ONE frame tx, without ever funding ETH. Without frame txs the thief had to (i) fund gas (the existing sweeper-bot dynamic), (ii) use 7702 sponsorship (needs delegation), or (iii) fund ETH and race. Frame txs + token paymaster removes the thief's ETH-funding step => it widens sweepability of gas-less compromised wallets, as the candidate's "twist" claims. Spec-supported; actual behaviour of the devnet paymaster/sidecar for token-paid frames not run.
 (b) Staking/reputation do NOT stop it (Sybil-only, no slashing; reputation only tracks inclusion rate).
 (c) No protocol rule favors the legitimate owner. Race = fee auction (10% bumps) or parallel nonce keys; mempool arrival order is not guaranteed to be binding (nodes admit both when keys disjoint).
 (d) Honest conclusion: the defence has to be at the paymaster/policy layer: a paymaster can read all later frames (FRAMEPARAM/FRAMEDATALOAD: EIP L1531 "paymasters... can observe user operation parameters before approval") and so can enforce "SENDER frames may only transfer to a destination committed in advance (recovery-address registry) ". That only works if the commitment pre-dates the leak or is bound to something the thief cannot set (the thief can set a registry entry with the same leaked key: first writer wins). So the only owner advantage is a PRE-leak commitment (e.g. registry/guardian), not a post-leak race. A paymaster 'refuse known sweeper delegate / destination blocklist' is a heuristic defence, trivially evaded by a fresh destination.
 UNKNOWABLE without running: (i) whether the devnet sidecar admits an unstaked/staked token paymaster tx that reads token balance (docs vs code differ: PR#6 vs ERC-8421); (ii) real inclusion ordering between a replacement and a disjoint-key tx under the miner (the devnet's single miner builds blocks from the privileged relay; ordering policy unknown); (iii) whether a token paymaster can be made safe against the 'zero out balance' frontrun without post_op repayment; (iv) gas/state-gas costs of ERC20 transfer+revoke in rescue frames.

## Q6 log: INTERVENTION analysis
(a) victim already 7702-delegated to a sweeper vs clean EOA:
 - Clean EOA (no code): default code applies (spec L725-738); workshop step_3 proves a code-less key can be a sponsored frame sender. Both owner and thief can transact via frame tx. Rescue and sweep are both feasible. 
 - Delegated to a sweeper (all five labelled delegates verified to contain no 0xAA opcode): the VERIFY frame executes the sweeper's bytecode (L450-451), which never calls APPROVE => tx invalid for BOTH parties. The forum claim "7702-delegated EOAs break frame-tx signature checks" is TRUE in this sense. Consequence: (1) a victim already delegated to CrimeEnjoyor cannot use a frame-tx rescue until the delegation is reset by a classic type-4 authorization (which needs a funded relayer, and the sweeper itself frontruns native ETH but a third-party relayer can submit the authorization -- authorization tuples are signed by the authority and submitted by anyone, per EIP-7702); (2) the thief likewise cannot use frame txs against such a wallet, but doesn't need to - the delegate IS the sweep mechanism. (3) The ERC20 sweep threat via frame txs is therefore specifically to CLEAN (non-delegated) leaked EOAs holding tokens and no ETH, and to wallets whose delegate is an 8141-aware account. This SHRINKS the measurable pool: the earlier scan's "delegated to labelled sweeper" population is largely outside the frame-tx threat model, since for those the sweeper already works without frame txs.
 - Devnet cannot test installing a delegation inside a frame (ethrex lacks SETDELEGATE opcode per sidecar docs); the type-4-reset-then-rescue path needs ordinary type-4 txs on the devnet (ethrex supports Prague-era 7702? not verified).
(b) public-mempool rescue vs alt-mempool rescue:
 - Public mempool (EIP L953, L1130-1142, L1093): a token paymaster that reads token.balanceOf(sender) violates the trace rule (SLOAD only tx.sender storage) and a non-canonical paymaster is capped at 1 pending tx (MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER=1). So the ERC20-paymaster rescue is NOT public-mempool-admissible; only the canonical ETH paymaster (ecrecover-signer, balance-reservation) or a code-less EOA sponsor (payer with empty code, only solvency rule) is. Hence in the public mempool the sponsor must be a plain ETH-funded EOA or the canonical paymaster -- which is signer-gated (human/service decides) and therefore CAN implement "only sponsor the owner" via off-chain authentication (e.g. a rescue service). 
 - Alt mempool: staked token paymaster admissible (STORAGE-032), REPUTATION-220 lets an unstaked good-reputation payer carry >1 pending txs. => alt mempool is exactly what makes the *permissionless token sweep* possible, and also what makes the *permissionless token rescue* possible. So S-A's 'only alt mempool makes this possible' relation to track is real. And that a non-alt (public) path exists for a signer-gated paymaster rescue weakens "needs the alt mempool" for the rescue half (the sweep half needs it).
