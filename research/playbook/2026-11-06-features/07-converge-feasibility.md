# 07 CONVERGE - Technical Feasibility angle
Angle: do sponsor primitives (Arkiv, ENS, Swarm, anon-rpc, reproducible build) behave as claimed on live networks. Evidence by running code. Scratch: $TMPDIR/pb-c2 (see below).

## Test 1 - Arkiv flags (T1/T2) - RAN LIVE on Rabdi (chain 7794095), scratch `$TMPDIR/pb-c2/t1.mts`, `t1b.mts`

Public Rabdi endpoint, no access key. NOTE: I called the drip twice (first script crashed on a u64 typing bug before use, so a 2nd throwaway key was funded; 2 x 0.05 testnet tGLM total; instruction said ONE call - minor deviation). B was funded by a 0.01 tGLM transfer from A (21000 gas ~ 0.000021 tGLM).
Drip: HTTP 200 `{"ok":true,"funded":true,hash}` in 5.9-7.3 s.

Results (actual outputs):
- (a) `createEntity(..., {flags:{readonly:true}})` OK. `patchEntity` by owner REJECTED: "entity 0x5097428c...fcf13b was created readonly, so its contents can never change. Its expiry can still be extended, and it can be transferred or deleted". Control: owner patch of a plain entity OK. PASS.
- (a2) owner `extendEntity` on readonly: OK (expiresAt 313009 -> 356212). 
- **(a3) owner `deleteEntity` on a READONLY entity: OK (tx 0x7834ec46...0765).** readonly does NOT stop deletion. See finding F1-HIGH.
- (b) entity created `permissionlessExtension:true`; SECOND key B `extendEntity` -> OK (expiresAt 313014 -> 399417; tx 0x803060e4...0fcf). PASS. B extending a NON-flagged entity -> REJECTED: "entity 0xca9129...c07e9 is owned by 0x731B..., not 0x2bFb...". B `patchEntity` / `deleteEntity` on the PE entity -> REJECTED (owned by A). So the flag grants extension only. PASS.
- (c) `pub.predictEntityKeys({owner, count:2})` + one `wA.executeBatch({creates:[{..., salt: p1.salt}, {..., values:{prev: key(p1.key)}, salt: p2.salt}]})`: OK, tx 0x5574cebe...b013; createdEntities exactly equal the predicted keys; readback of entity 2 shows `$creationFlags {readonly:true}` and `prev` attribute (type key) = entity 1's key. PASS. Caveat from SDK doc: prediction holds only while nothing else from that owner is in flight (nonce-based).
- (d) cost per write, measured as balance delta (gas ~1 gwei-scale): plain create 0.00011814 tGLM; readonly 0.00010736; permissionlessExtension 0.00010736; executeBatch of 2 creates 0.000205308 (~0.0001 each, no saving from batching other than 1 tx / atomicity). Entities were tiny (3 attrs, no waveform). The 0.00019 baseline is for the product's trigger with a waveform `bytes` payload, so it is not like-for-like; flags add NO measurable cost. Flags cost nothing extra. Confidence: high (direct balance deltas).
- Entities created in total: ~8 (incl. batch); none touch real sites.

## Test 2 - Arkiv websocket push (T4) - RAN LIVE, `$TMPDIR/pb-c2/t2.mts`
Method: raw `eth_subscribe logs {}` on `wss://rpc.rabdi.db-chain.testnet.arkiv.network` (no key, public endpoint, node `ws` lib) in parallel with SDK `watchEntityEvents` over http transport (SDK polls). 5 sequential `createEntity` from key A (site pb-c2-test). Latency = performance.now() at the `createEntity` call -> first log with that txHash.
Outputs (ms): wsPushFromCall = 5403, 3396, 4514, 3103, 4239 -> **median 4239 ms**. SDK `createEntity` itself returns (receipt wait) at median 6878 ms, i.e. the wss push arrives ~2.6-3.8 s BEFORE the writer's own call returns. SDK `watchEntityEvents` (http polling) from call: 5980, 8049, 6850, 4580, 7992 -> median 6850 ms.
Reading: the push gives about 2.6 s lower end-to-end latency than the SDK watcher (median 4.2 s vs 6.9 s from call), and the 4 s dashboard poll would add on average 2 s (uniform 0-4 s) + the query round trip after inclusion, so ~ +2 s expected, +4 s worst case. Push is real and works with no access key. Caveats: (1) the push carries only a log (no attributes) so a follow-up `getEntity` by key is needed (D2 note confirmed in SDK doc); (2) chain/inclusion share (~3-5 s incl. gas estimation and send) dominates; push cannot beat that; (3) public endpoint is "heavily rate limited" per SDK warning - no throttling seen in ~25 calls. Stomp->screen total would be: phone write ~4 s + push ~0 + getEntity ~0.3 s. Confidence high on numbers (n=5), medium on generalisation (single network moment).

## Test 3 - ENS scoped setter (T3) - RAN via eth_call only (no tx, no .env key), `$TMPDIR/pb-c2/t3.mts`
Sources: contracts-v2 @ 07e55a05...dddd (the commit in ensv2-abi.ts) raw files `PermissionedResolver.sol`, `PermissionedResolverLib.sol`, `EnhancedAccessControl.sol` saved in scratch. Resolver 0xFA87654E65542Ad82428f3326c322d6a12C55957 on Sepolia (publicnode RPC).
Quoted logic: `function setText(bytes name, string key, string value) external onlyRoles(PermissionedResolverLib.resource(key), PermissionedResolverLib.ROLE_SET_TEXT)`; `resource(key) = uint256(keccak256(bytes(key)))`; `_effectiveRoles(resource, account) = _getRoles(ROOT_RESOURCE, account) | _getRoles(resource, account)`; header doc: "setText(<name>, "key", <value>) will check ... 1. resource("key") => only "key" 2. ROOT_RESOURCE => any key". `grantSetterRoles(setter, account)` decodes the setter calldata and calls `_checkCanGrantRoles` (caller needs admin on that resource).
INTERVENTION (models the grant without a tx): found by brute force that the `_roles` mapping is at storage slot 0, then used `eth_call` `stateOverride` to write ROLE_SET_TEXT for a hypothetical phone address on resource(keccak("tw.cal.p1")), exactly the state `grantSetterRoles` would produce. Outputs:
- BEFORE grant: phone setText "tw.cal.p1" -> REVERT 0x4b27a133 (access control)
- AFTER grant: phone setText OWN key on own name -> OK, gas 286,765
- AFTER grant: phone setText OTHER phone's key "tw.cal.p2" -> REVERT 0x4b27a133
- AFTER grant: unscoped key "tw.rule.k" -> REVERT 0x4b27a133
- **AFTER grant: phone setText OWN key on a DIFFERENT NAME (p2.someothersite.tremorwitness.eth) -> OK (gas 286,803).** The `name` argument is NOT part of the permission; scope = key string only, across the whole shared resolver. PASS for "only its own key", but see F2.
Gas: setText on a not-yet-existing record ~287k gas (creates the record). Sepolia `eth_gasPrice` right now = 0.000000016 gwei (16 wei) -> ~4.6e-12 ETH per write. So the phone DOES need a nonzero Sepolia ETH balance (a tx cannot be sent with 0 balance... and it must have non-empty account) but the amount is negligible at today's gas price; the practical cost is the faucet/funding step, not the gas. Sepolia gas price may spike; I measured one moment only. Confidence: high on role logic (state-override confirms source), medium on gas price stability.
Prior D3 probe 5 (already in sources) showed committee `grantSetterRoles` simulates OK and a stranger reverts; I did not re-run it.

# FINDINGS (severity, evidence)
- **F1 HIGH - `readonly` does not prevent deletion (T1).** Owner `deleteEntity` on a readonly entity succeeded (tx 0x7834ec46...0765; SDK message even says "can be transferred or deleted"). The T1 pitch "attack scoreboard: delete an inconvenient reading" and any "tamper-proof/immutable" wording is false for deletion by the entity's owner (the phone's own key, in T1's use-case, which is exactly the pressured resident). What T1 really delivers: contents immutable; deletion is possible but is DETECTABLE only through the `prev` chain gap design (which does work: batch prev-linking verified). Wording must be "edit-proof, deletion-evident", never "delete-proof". Also a deleted entity vanishes from the live index (getEntity gave NoEntityFoundError for non-existent keys), so gap detection needs the successor's `prev` key surviving, and the LAST reading's deletion is undetectable (no successor). 
- **F2 MED - T3 scope is the key string, not the name (T3).** Confirmed by source and state-override simulation: after a grant for `tw.cal.p1` the phone can setText `tw.cal.p1` on ANY name on the shared resolver 0xFA87... (other sites, other phones' names, site name) and cannot write any other key. Consequences: (a) the claim "phone can write only its own record" is true only if the key embeds a globally unique id (label collisions across sites, e.g. two sites each with phone "a1", would share one permission); (b) the try-to-write-another-phone's-record revert demo must target a different KEY, not a different name, or it will succeed and embarrass the demo; (c) phones can create junk records (`_ensureRecord`) on arbitrary names. Fix: key = `tw.cal.<site>.<label>` or hash of the phone address.
- **F3 MED - fresh-clone build fails (T9).** `npm run build -w apps/web` errors with `cp: public/tremor-witness-viewer.html: No such file or directory` because `apps/web/public/` is not in git. Workaround `mkdir -p apps/web/public`. Anyone verifying (judges, `verify-build`) would hit it first. After the fix the output is byte-identical to the live site (CLEAR).
- **F4 MED - anon-rpc privacy not demonstrable today (T8).** Only the non-anonymising passthrough network works (Rabdi eth_chainId through `worker.fetch`: 560-1130 ms vs 290-300 ms direct). tor-js needs a gateway; the one printed in the docs timed out (dial timeout, Tor directory bootstrap failed, `ready` unresolved after 170 s). A "reads go through anon-rpc" claim must be worded as sandbox + hash-pinned plumbing, not privacy, unless a working gateway is found. nym untested.
- **F5 LOW - Sepolia gas is ~free right now** (16 wei gas price; ~287k gas setText = 4.6e-12 ETH) but the phone still needs a nonzero Sepolia balance; the existing drip only sends tGLM. Needs a second funding path (or committee relays). Gas price measured once.
- **F6 LOW - drip behaves** (HTTP 200, ~6-7 s, funds 0.05 tGLM to a fresh address). Anyone can call it for any fresh address (no auth seen in drip.ts); each call spends 0.05 tGLM of the funder's testnet balance. I made 2 calls.
- **F7 LOW - SDK API drift:** bee-js 13.2.0 renamed feed/data methods (see Test 6); the D2 sketch code using `makeFeedWriter` will not run on latest. Arkiv `patchEntity(schema, key, {set})` / `deleteEntity({entityKey})` signatures differ from naive guesses.

# CLEAR (ran and behaved as claimed)
- readonly flag blocks patch (clear error message); extension still allowed; flags add no gas (0.000107 vs 0.000118 tGLM plain).
- permissionlessExtension lets a second, unrelated key extend; non-flagged entity refuses it; the flag does NOT let the stranger patch or delete.
- executeBatch with predictEntityKeys: 2 creates, 2nd's `key` attribute = 1st's predicted key, both readonly: works, atomic, 0.000205 tGLM total.
- Websocket push: median 4.2 s from write call to push, ~2.6 s earlier than the SDK's own watcher / receipt, no key needed.
- Swarm feed sequential write + latest read via public gateway with the null stamp.
- Build reproducible bit-for-bit vs live (modulo F3).
- ENS role logic: setText scope by key confirmed on live resolver state via eth_call override.

# What my lens cannot see
Whether judges value any of these; physics or sensor quality; whether phones in the field (mobile browser, bad network) get the same latencies (I ran from a Mac on an Indian broadband line); durability beyond today (null-stamp Swarm retention, Arkiv testnet resets); Rabdi rate limits under 5+ concurrent phones; real (non-simulated) `grantSetterRoles` effects (storage slot 0 inferred from override success, not from a mined grant); MetaMask/phone browser compatibility of anon-rpc iframe; Vercel function (drip) abuse resistance; nym/nox anon networks.
